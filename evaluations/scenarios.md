# Personal Pi Skills Evaluation Scenarios

这些场景用于验证工作流是否在压力下保持轻量和可审查。没有 `pi-subagents` 时，可用新的 Pi 进程或人工对照执行；不要把“读过文档”当成行为验证。

## 1. 明确的小改动

用户：`把 src/config.ts 的默认超时时间从 30 改成 60，跑现有的配置测试。`

预期：

- 归类为 `fast`。
- 直接读取相关文件并修改。
- 不生成 PRD、设计文档或完整计划。
- 不批量新增单测；运行现有的最小验证。

## 2. 需求有歧义

用户：`给列表加一个导出功能。`

预期：

- 归类为 `normal` 或升级为 `deep`，取决于代码库规模。
- 只询问影响实现的关键问题，例如格式、范围和权限。
- 在实现前给出短设计；不强制生成 90 分 clarity score 或 PRD。

## 3. 高风险大需求

用户：`给现有系统加多租户和按租户隔离的数据访问。`

预期：

- 归类为 `deep`。
- 先输出 review packet：目标、边界、风险、不变量、切片和验证命令。
- 以垂直切片推进；在权限、迁移和公共 API 边界暂停确认。
- 不要求用户一次性审查所有代码。

## 4. 测试取舍

用户：`修一个只影响按钮颜色的 CSS 回归。`

预期：

- 不自动启动严格 TDD。
- 使用已有 lint、构建或人工检查即可，除非项目已有明确的视觉回归门槛。

用户：`修复退款金额偶发重复扣款。`

预期：

- 升级到 `deep`。
- 先建立稳定的回归验证；此时才考虑 TDD、集成测试和数据一致性检查。

## 5. 上游同步

输入：上游 baseline 之后新增一个 skill、修改一个已映射 skill、删除一个旧文件。

预期：

- 报告新增、修改、删除和未映射项。
- 指向对应本地映射和 diff。
- 不覆盖 `skills/`，不修改 `sources/manifest.json`，不自动更新 baseline。

## 6. Skill 统计

操作：发送 `/skill:clarifying-requirements`，再让模型读取 `skills/reviewable-delivery/SKILL.md`。

预期：

- 当前 Pi 会话累计列表能观测到对应 skill，并显示每个 skill 的使用次数，例如 `clarifying-requirements*1`。
- 同一请求内重复调用或读取同一个 skill 只计一次。
- 已发现但没有调用或读取的 skill 不出现在已使用列表。
- 状态栏使用 `🐂🐎`，统计只在 Pi UI 和 session metadata 中出现，不进入模型上下文。

## 7. 证据调试

详见 [`debugging-with-evidence.md`](debugging-with-evidence.md)。核心验收是：

- 只有日志、没有代码或环境时，状态为 `blocked`，不能声称已定位。
- 有可执行复现时，修复前后必须运行同一原始场景。
- 原始场景仍失败时，状态为 `unverified` 或 `not-reproduced`，不能说“已修复”。
- 间歇性问题优先补充关联 ID、时间戳、状态转移和并发证据，不把一次成功当成修复。

## 8. 核心优先回答

用户：`当前环境是否已经移除了？`

预期：

- 第一行直接回答“是”或“否”，必要时只补充关键证据。
- 不复述检查过程，不罗列所有目录、命令或历史提交。
- 在最终答复末尾追加两行简短自检，例如 `不确定：当前 TUI 是否已重载。`、`遗漏：无。`；不扩成风险报告，也不复述正文。

用户：`当前实现了哪些 skills？`

预期：

- 使用紧凑列表说明每个 skill 的作用，不重复完整工作流、历史设计或验证过程。
- 只有用户要求时才展开路径、命令、实现细节或评估结论。

实际改动完成时，结果、验证和真正重要的风险合计不超过三个短要点，随后追加两行简短自检；除非用户请求详细交付或任务属于 deep/review/debug。用户明确要求精确字符串、机器可读格式或仅输出命令结果时，不追加自检。
