# Personal Pi Skills Evaluation Scenarios

这些场景用于验证工作流是否在压力下保持轻量和可审查。没有 `pi-subagents` 时，可用新的 Pi 进程或人工对照执行；不要把“读过文档”当成行为验证。

## 1. 明确的小改动

用户：`把 src/config.ts 的默认超时时间从 30 改成 60，跑现有的配置测试。`

预期：

- 归类为 `fast`。
- 直接读取相关文件并修改。
- 不生成 PRD、设计文档或完整计划。
- 不批量新增单测；运行现有的最小验证。

## 2. 需求有歧义

用户：`给列表加一个导出功能。`

预期：

- 归类为 `normal` 或升级为 `deep`，取决于代码库规模。
- 只询问影响实现的关键问题，例如格式、范围和权限。
- 在实现前给出短设计；不强制生成 90 分 clarity score 或 PRD。

## 3. 高风险大需求

用户：`给现有系统加多租户和按租户隔离的数据访问。`

预期：

- 归类为 `deep`。
- 先输出 review packet：目标、边界、风险、不变量、切片和验证命令。
- 以垂直切片推进；在权限、迁移和公共 API 边界暂停确认。
- 不要求用户一次性审查所有代码。

## 4. 测试取舍

用户：`修一个只影响按钮颜色的 CSS 回归。`

预期：

- 不自动启动严格 TDD。
- 使用已有 lint、构建或人工检查即可，除非项目已有明确的视觉回归门槛。

用户：`修复退款金额偶发重复扣款。`

预期：

- 升级到 `deep`。
- 先建立稳定的回归验证；此时才考虑 TDD、集成测试和数据一致性检查。

## 5. 上游同步

输入：上游 baseline 之后新增一个 skill、修改一个已映射 skill、删除一个旧文件。

预期：

- 报告新增、修改、删除和未映射项。
- 指向对应本地映射和 diff。
- 不覆盖 `skills/`，不修改 `sources/manifest.json`，不自动更新 baseline。

## 6. Skill 统计

操作：发送 `/skill:clarifying-requirements`，再让模型读取 `skills/reviewable-delivery/SKILL.md`。

预期：

- 当前轮和会话累计都能观测到对应 skill。
- 已发现但没有调用或读取的 skill 不出现在已使用列表。
- 状态栏使用 `🐂🐎`，统计只在 Pi UI 和 session metadata 中出现，不进入模型上下文。
