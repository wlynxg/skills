# 完成声明前的验收与证据

没有与声明范围匹配、且在最后相关修改后取得的实际证据，不声称完成、修复、通过或“没有问题”。能确认的是覆盖过的行为，不是不存在所有缺陷。

## 先核对需求，不只核对代码

回到用户原始要求、获批设计和验收项，逐项确认：

- **实现**：功能是否真实存在，而不是只定义类型、建表、写文档或留位？
- **接入**：实际入口、调用方、配置、数据写入/读取和必要副作用是否贯通？
- **验证**：当前改动后的结果是否满足该项要求？缺失、未运行、skip 或阻塞分别标明。

不能只检查自己最后改的文件，也不能用自己写的单测重新定义需求。不得自行从验收范围删掉难做的项；范围变更先取得批准。

## 证据门

1. **识别**：哪条命令、请求或操作能证明这个具体结果？验证手段必须覆盖声明的层级。
2. **执行**：实际运行，保存命令、环境和结果；旧结果只有明确不受后续修改影响时才能复用。
3. **检查**：读取退出码、失败/skip 数以及实际内容和副作用，不只看 HTTP 200。原始问题按同一复现条件复测。
4. **对照**：将证据对应到验收项，确认未实现与未验证的范围，再给结论。

构建通过只证明构建；局部单测只证明测到的分支；mock 或选择评估不证明真实业务端到端；缺少数据库而跳过的集成测试不算通过。

## 简洁但不能假完成

按实际情况汇报，不机械要求大报告：

```text
已验证：验收项与决定性命令/结果，必要时链接证据。
未实现：获批范围中仍缺少的能力。
未验证/阻塞：没有运行的场景、原因与最小解除条件。
结论：完整范围已验证 / 部分完成 / unverified / blocked。
```

没有缺口时不凑风险；有缺口时不得用一句“全部完成”覆盖。只做了代码修改但无法运行时，明确 `unverified`，不要说“改动已完成”暗示功能已可用。

汇报通常用少量要点，无需贴全部命令输出；有证据的概述或链接即可，但不能以简洁为由隐藏验收缺口。用户再要求“检查一遍”时重新检查原始要求、真实入口和已知失败边界，不只再读一次 diff。

## 停止条件

- 验收项缺实现、集成被跳过、真实入口未接入：只能报告部分结果。
- 用户原始问题仍失败：回到 `debugging-with-evidence`，不靠额外补丁或推测词结束。
- 检查发现尚未批准的业务口径、兼容机制或范围变化：先补充确认，不为了凑完成状态暗自实现。
