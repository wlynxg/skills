# Clarifying Requirements

需求澄清的目标是消除会导致返工的歧义与设计分歧，在动手编码前与用户达成设计共识，同时避免把任务过度仪式化成冗长 PRD。

## Hard Gate（硬门禁）

**凡是涉及新功能开发（Feature）、增改接口契约、改变已有业务流程的请求：严禁在未经用户确认前直接动写或修改业务代码。**
先读代码，然后必须输出【核心设计与确认契约】，并**暂停等待用户确认**（"请确认以上设计是否符合预期？"）。未获明确答复前，不得私自假设并推进编码。

## First Check

先读现有项目结构、相关入口和已有约定。若请求是**纯现有缺陷修复、格式/配置微调**，且已经明确指明了具体文件、函数与修改内容，可直接执行，无需打断。
但**只要是在做“新功能/加接口/改业务流”**，即使用户指令非常简短（如“帮我加个根据用户查订单的接口”），也必须先探查代码，给出设计确认。

## Completeness Checklist（防遗漏自查）

在给出设计前，强制按以下维度穷举，严禁只顾 Happy Path：

1. **入参与出参契约**：字段定义、命名（对外 API 严禁混入非规范命名）、空数据返回格式。
2. **边界与异常**：数据不存在、非法输入、重复请求、下游超时或依赖失败时怎么处理？
3. **副作用与依赖**：是否涉及缓存失效/更新、事件/通知、事务、数据库字段/索引变更？
4. **隐式假设暴露**：自己在实现中“默认准备这么做”的地方，必须显式列为假设让用户检验，严禁暗箱操作。

## Design Confirmation Contract（设计确认模板）

在探查完代码后，向用户输出一段精炼明确的设计契约（在聊天中输出，控制在 15-20 行以内，不创建冗余 spec 文件）：

```markdown
### 核心设计与确认

- **功能范围**：...（明确包含什么，不包含什么）
- **实现方案与改动点**：
  - 核心入口/文件：`...`
  - 接口/数据结构（如涉及）：入参 `...` / 返回 `...`
  - 复用现有组件：复用 `...`
- **异常与边界策略**：
  - 空数据/未找到：...
  - 错误与重试：...
- **关键假设与决策点（请确认）**：
  1. 我假设 ...；如果不符合，请指出方案。
  2. [如有互斥方案或分歧点，列出 1-2 个选项让用户二选一]

👉 **确认以上设计符合预期后我将开始实现，是否继续？**
```

## Stop Conditions

- 用户说 `澄清` 或 `/clarify`：只澄清并输出契约，不写代码。
- 给出设计确认后：**停止工具调用，等待用户回复确认。**
- 发现认证、权限、金额、迁移、并发、数据丢失或不可逆行为：升级到 deep，并使用 `reviewable-delivery`。
- 仍有多个互斥方案：列出最多 2-3 个方案，给出推荐和取舍，让用户选择。

## Anti-Patterns

- **暗箱假设**：以为用户需求简单，就不问不管，脑补接口字段和异常处理直接写代码。
- **只顾 Happy Path**：只写主流程代码，对空值、错误码、边界情况视而不见。
- 不生成 clarity score，不追求 90/100。
- 不为了形式补齐“用户故事、风险矩阵、四阶段 PRD”。
- 不问已经能从现有代码一眼看出的既定事实（应问业务语义、决策取舍与边界）。
- 不在澄清阶段偷偷实现一半。
