# 需求理解与设计确认

把简单需求补成用户能认可、纠正和验收的设计，不替用户脑补业务，也不把每个任务变成 PRD。

## 先理解再提问

先读相关入口、真实调用方、已有类似实现和权威约定。分清：用户明确要求、代码事实、助手建议、尚未确认的假设。现有代码不是业务设计的唯一权威。

优先澄清会改变结果的问题：用户得到什么、成功如何判断、哪些角色/状态/数据属于范围，以及真实失败行为。一次通常问 1-3 个最高影响问题，给推荐和理由；已能从代码确认的事实不问，内部技术细节自己决策。

重要未知不能当作低风险默认值。确有互斥方案时给 2-3 个选项及取舍，不为了凑方案制造复杂度。用户回答部分问题后，明确还剩哪些重要未决点。

## 适用性与完整性检查

按当前任务检查以下维度；分别判定“已有保证 / 当前必要 / 不适用 / 未决”，不是全部新增实现，也不强制输出大矩阵：

1. **用户结果**：真实入口是否接入？权限、输入输出、空数据、错误和关键状态是否可验收？
2. **真实影响**：调用方、数据流、缓存/事件/事务、配置和文档是否受到本次改动影响？
3. **阶段与消费者**：当前契约是否已发布或需稳定？消费者能否同步更新？搜不到调用不等于没有外部消费者。
4. **数据与迁移**：是否存在要保留的资料？一次性离线处理是否足够？未上线不代表可删除数据。
5. **新增复杂度**：兼容别名、重试/降级、配置旋钮、抽象或正式命令，哪个当前用例需要？已有能力为何不够？
6. **验收依据**：每个要求用什么结果验证？哪些环境限制会导致无法验证？

默认遵循 `adaptive-workflow` 的阶段策略：可同步更新的未发布契约干净替换；必要兼容集中边界并明确删除条件；一次性任务不默认形成常驻代码；可信内部不变量不做推测性重复防御。

范围包含与不包含都要有用户依据。不得把自己偏好的技术方案写成“明确不做”“一期不做”，也不得因为 YAGNI 把用户明确要求改成只留表或以后做。

## 短设计契约

普通任务在聊天中按需给出，不硬凑 15-20 行、评分或 spec 文件：

```text
目标与验收：用户应得到什么；用什么结果判断。
已确认范围：包含什么；排除项的依据。
阶段与影响：契约/消费者/存量数据的事实或重要未知。
方案：核心流程、复用点、真实异常处理与改动边界。
兼容/迁移与新增常驻机制：无；或对象、必要性、成本与删除条件。
待确认：尚未决定的重要事项、推荐及取舍。
```

仅列适用内容，不能把重要未决点隐藏在“按默认处理”里。架构级或跨边界高风险任务使用 `reviewable-delivery`，方案文档不自动提交。

## 批准门禁

- 新功能、契约或流程变化：设计发出后停止实施，等待用户明确批准；不能边让用户看方案边写业务代码。
- 已有完整且明确批准的设计，或用户看过方案后明确委托你在该范围决定内部实现：无需重复批准，按获批范围推进。
- “继续”“赶紧做”不自动补齐重要未决业务口径；部分答复不等于批准其他重要决策。涉及新兼容路径、常驻工具或范围变化时补充确认。
- 用户要求 `澄清`/`只做方案`：只读探索与方案，不实施。
- 明确的局部修复、精确文案/配置调整且没有新重要决策：直接做，不反复澄清。
- 发现权限、金额、迁移、并发一致性或不可逆风险：升级流程，但不把本来没有要求的风险机制一并实现。

## 反例

“给列表加导出”：先查现有权限、数据范围和导出能力，问格式/范围等关键问题，给推荐并待批；不要自行全量导出，也不要顺手造队列、分页快照与通用导出框架。

“已批准内部字段重命名；未发布，调用方可同步更新”：直接更新调用方和验收，不为了旧测试保留别名，也不重新要求用户批准同一设计。
